VEPeagle — Manual

Reference documentation for VEPeagle (gate + five stimuli)

What this suite is

Four stimulus pages for the canonical visual-evoked-potential responses — flash, pattern reversal, pattern onset and motion onset — and an oddball page for responses to rare stimuli, plus the tools they need around them. Everything runs in a browser from a folder on disk. There is no installation, no build step, no server and no network connection.

The name runs VEP and eagle together. The eagle is the Orlice — Czech for a female eagle, and the river that joins the Elbe at Hradec Králové, where the suite was written.

Four ideas shape how it works, and knowing them makes the rest predictable.

  • Each stimulus page is self-sufficient. It can be opened on its own, configured, and run. The gate page is a convenience that fills the shared parameters in for you, not a component the stimuli depend on.
  • Parameters live in the URL. Whatever you set is reflected in the link the page shows you. Copy that link and you have the condition: it reopens identically, on this machine or another, and it can go into a protocol or a bookmark. This is also how the gate hands settings over.
  • The calibration is a file. A .json written by the calibration page. It travels in the URL and is named in the log, so a recording can always be traced back to the display state it was made under. Browser storage is only ever a shortcut.
  • The log is the record. Every event carries a timestamp from performance.now(), alongside the full parameter set, the calibration in force and which renderer drew the frames. The APA paragraph each page produces is written from the same values.

Quick start

The shortest path from a folder of files to a recording.

  1. Open display_calibration.html, measure the display, and press Open gate with this calibration. The gate opens with the calibration already loaded. (Skipping this is allowed — the stimuli then assume sRGB and work in relative units, and no luminance is reported.)
  2. In the gate, set the screen width in pixels and centimeters, the viewing distance and the sync dot. The gate remembers them.
  3. Press the launch button for the stimulus you want. It opens with everything filled in.
  4. Set the stimulus-specific parameters: frequency, duration, number of trials, pattern type, colors, fixation cross and masks.
  5. Tick Save log and type a session note if you want a record.
  6. Press ↗ New window to put the stimulus on the presentation screen, tick Fullscreen, and click once in that window (or press F).
  7. Press Start. A short frame-rate measurement runs first, then the pre-stimulus delay, then the stimulation, then a post-stimulus baseline of the same length as the delay.
  8. Ctrl+Space stops at any point. In full-screen, Esc leaves full-screen, which also ends the run and saves the log.
The link is the condition. Copy the reproducible link the stimulus page shows you and keep it with the protocol. It holds every parameter and the calibration in one line, and reopening it reproduces the setting exactly.

Changing a stimulus

Every field on a stimulus page takes effect the moment you change it, and the reproducible link below the form updates with it. Nothing needs saving and nothing needs reloading.

  • Set a contrast rather than colors. Type a Michelson contrast in percent and a mean luminance, then press Apply to colors. The colors are computed for you and stay editable afterwards — see Contrast and photometry.
  • Reuse a condition. Copy the URL. Bookmarks and protocol lines both work; the calibration travels with it.
  • Change the calibration for one page only. Load a .json on the stimulus page itself; it overrides whatever the link carried, and the new link carries the new one.
  • Force the CPU renderer. Add &webgl=0 to the URL. The renderer actually used is recorded in the log either way.

Installation & requirements

Put every file listed above in one directory and double-click vep_gate.html, or any stimulus page directly. No build step, package manager or local server is required.

The shared files have to sit beside the pages: every page loads vep.css, the gate and the calibration page load vep_engine.js, and the five stimuli load vep_engine.js, vep_page.js and p5.min.js. A missing file is reported rather than failing quietly: the gate says so in its calibration status line, and a stimulus page names the file in its status line and keeps Start disabled. Without vep.css the pages still load, but unstyled; put it back before recording.

Browser requirements

  • Any current Chromium-based browser (Chrome, Edge, Brave) or Firefox.
  • Hardware-accelerated rendering enabled (default).
  • A display refresh rate stable enough for your timing tolerance — typically 60–144 Hz LCD or higher. The actual rate is measured at session start (see below).
file:// vs. http:// — does it matter?

For the stimulus, no — every page runs the same from the local file system or from a web server, with requestAnimationFrame, performance.now(), fullscreen and the clipboard available in both, and links work as bookmarks either way.

What differs is browser storage. Over file:// each file keeps its own, so one page cannot read what another stored. That is why everything a page needs from another — the parameters, the calibration, even the light or dark theme — travels in the link rather than in storage, and why the suite behaves the same whichever way it is opened. Served over http:// (for example python -m http.server), the pages share one store, which only means that remembered conveniences such as the last calibration are shared too.

Hardware recommendations

  • Display: CRT or low-latency LCD. Avoid TVs with motion smoothing.
  • Photodiode: Affixed to the screen at the synchronization dot location (configurable; default top-left, 32 px × 32 px). The dot shows its trigger color (white by default) during a sync event and is black otherwise, so the photodiode signal is a clean step. With an RGB photodiode, choose a primary color for the dot; see Synchronization.
  • Viewing distance and screen width: Both must be measured physically and entered on the gate or stimulus page; the pixel-per-degree value is derived from these numbers.
The colors in the form are code values, not measured light. What the light, dark, flash, blank, fixation and mask colors actually produce on screen depends on the monitor's gamma, brightness and contrast settings and on any color management profile. For a published study, measure the display on the calibration page and report the resulting cd/m² — see Luminance calibration.

Recommended workflow

  1. Calibrate the display — on the first session, and after any change of monitor, brightness or profile. Open display_calibration.html, choose a model (sRGB to get going, Measured for anything you intend to publish) and for the measured model step through the guided photometer sequence. Download the .json — that file is the record of the display state and belongs with the recording. Then press Open gate with this calibration.
  2. Set the shared parameters in the gate: screen geometry and viewing distance, sync dot, and the session note.
  3. Launch a stimulus from the gate. It opens in a new tab with those parameters and the calibration already in place.
  4. Set the stimulus-specific parameters: timing, pattern type, check size or spatial frequency, fixation cross and masks, and the colors — either directly or by asking for a contrast and a mean luminance. To keep the result as a condition, copy the Reproducible link below the form and add it in the gate.
  5. Tick Save log and fill in the session note if you want a JSON record. The note can still be typed while a run is in progress.
  6. Put the stimulus where the subject will see it. Press ↗ New window and move that window to the presentation screen. With Fullscreen ticked, Start stays locked until that window really is full-screen — one click in it, or F, is enough.
  7. Press Start. A frame-rate measurement runs first, then the pre-stimulus delay, the stimulation itself, and finally a post-stimulus baseline of the same length as the delay. The stimulus window shows FINISHED when it is over.
  8. Copy the APA paragraph from APA-style report below the form; a click copies it. It describes the parameters, the calibration and the renderer that were actually used.

The reproducible link is also a preset: bookmarked or added to the protocol, it reopens the condition exactly as it was (see Quick start).

Using the gate page

The gate page (vep_gate.html) is the recommended starting point. It holds two things: the conditions of an examination, in order, and the environment they run in — the screen, the room, the synchronization patch and the display calibration. Every condition launched from the gate gets the gate's environment; what the stimulus is stays with the condition.

The dividing line. The gate owns the screen width in pixels and centimeters, the viewing distance, the display refresh rate, the sync dot (position, size, on-time, color), Fullscreen, Save log, the session note and the calibration. Everything else — pattern, colors, contrast, timing, fixation cross, masks — belongs to the stimulus page and is stored with the condition. Fixation and masks are deliberately not in the gate: a central mask changes which part of the retina is stimulated, so it is part of the stimulus and may differ between the conditions of one protocol.

Sections

  • Session — the session note written into every log, and the Fullscreen and Save log switches applied to every condition.
  • Conditions — the protocol. Each row has Run, Page, ↻, ↑ and ✕; see below.
  • Protocol file — download the protocol as .json, load one, or clear the list.
  • Screen & room — width in px and cm, viewing distance, and the display refresh rate. Collapsed, with the values shown in its header.
  • Display calibration — the calibration in force, with its type, age and where it came from.
  • Synchronization — sync dot position, size, on-time and the trigger color of each stimulus. Collapsed, with the values shown in its header.
  • Open a stimulus page — launch tiles for building a new condition.

What the gate remembers

The screen, room and synchronization settings and the two switches are remembered in this browser, so the gate reopens as you left it. The session note is not remembered: it names a subject, and carrying it into the next session would label someone else's recording. The last calibration you gave the gate is remembered too.

Following the VEP Gate link at the bottom of a stimulus page hands that page's screen and sync values back to the gate. If they differ from what the gate had, a notice lists the changes, with Undo to go back.

The protocol file records the environment beside the conditions, so the file alone documents how the study was run. Loading it offers those settings rather than imposing them, because the same protocol is often run on a different monitor.

Browser storage is a shortcut, not an archive. The protocol the gate remembers disappears when browsing data is cleared and does not exist in another browser or on another machine. Keep the protocol file and the calibration .json with the study — see Luminance calibration for the same point about the calibration.

Autostart (Run)

Run opens the stimulus without its settings panel. A confirmation screen shows the figures worth checking before a recording — stimulus, trials, field size, contrast, calibration, logging — and names any parameter that is out of range or not recognized. Clicking Start there enters full-screen and begins.

When the run ends, by completion or by Ctrl+Space, the window shows FINISHED and the name of the saved log, waits until the file has been saved, then counts down five seconds and closes itself. A click during the countdown keeps it open. Only a window opened by the gate's link can be closed this way; any other says so and stays open.

The technical version: how a condition link is built

Stored: the stimulus file and every parameter except the shared keys (screen_width_px, screen_width_cm, view_distance_cm, displayRefreshHz, useFullscreen, dot_x, dot_y, dotSize, syncDotFrames, hexSync1–hexSync3, enableLogging, note, cal, cal_name) and the launch keys autostart, parity and theme. The same split is applied whenever a condition enters the protocol: Add, ↻, a loaded protocol file, and a list left in browser storage by an older version.

At launch the gate writes its own values for every shared key into the stored link. An empty field removes the key, so the stimulus falls back to its own default (an empty display refresh rate, for instance, is simply not reported). The calibration is replaced the same way: with none in the gate, the condition runs without one, rather than with whatever happened to be embedded in an old link.

The sync colors are written per page: hexSync1 goes to every page, hexSync2 and hexSync3 only to pages that present several stimuli. A page started with autostart refuses parameters it does not know, so sending the extra colors to a single-stimulus page would stop it.

The environment is kept in browser storage under vep_gate_env, the protocol under vep_protocol, and the calibration under vep_gamma_calibration.

Keys

Ctrl+Space stops the run, from either window, and is the only stop key. Space alone pauses and resumes. In the stimulus window, F or a click enters full-screen between sessions.

Esc is reserved by the browser for leaving full-screen and is not passed to the page while full-screen. Leaving full-screen during a run is treated as stopping it: the run ends and the log is saved. In a windowed run Esc does nothing, and the status line says to press Ctrl+Space instead.

Typing in the session note or any other field is never intercepted: the shortcuts stand down while a text field has focus, which is why stopping is on Ctrl+Space rather than a bare key.

Presenting full-screen

A browser only grants full-screen to the window that asks for it, and only in response to something the operator did in that window. The stimulus window therefore has to enter full-screen itself: tick Fullscreen and then click once in the stimulus window, or press F there. Ticking the box while that window is already open is enough — it picks the change up and puts the prompt back on screen, so there is no need to close and reopen it.

Start stays disabled until the stimulus window reports that it is presenting full-screen. An OS-maximized window or a macOS virtual desktop counts: what matters is that nothing else is visible around the stimulus, not which mechanism achieved it.

Why the gate on Start exists at all

Browser chrome, a taskbar or a second window's edge inside the subject's field of view changes the mean luminance of the display and adds contours the stimulus did not put there. Neither is visible in the log afterwards. Blocking the start is the only point at which that can still be caught, so the check is deliberately strict: the stimulus window has to say it is full-screen before the run can begin.

What happens after Start

  1. A frame-rate measurement, about one second — see Frame rate measurement.
  2. The pre-stimulus delay (Start delay), showing the blank or background field.
  3. The stimulation itself.
  4. A post-stimulus baseline of the same length as the start delay, so the epoch after the last event is recorded under the same conditions as the one before the first.
  5. The stimulus window shows FINISHED and the main window returns to its resting state. The log, if requested, is offered for download at this point.

Screen calibration

Three parameters define the geometry of the experimental setup. Pixel-per-degree values derived here are used to set stimulus spatial scale. For accurate luminance reporting in cd/m², also run the display calibration wizard — see Luminance calibration.

ParameterSymbolTypical valueSource
Screen width (pixels)Wpx1920Auto-detected, in CSS pixels
Screen width (cm)Wcm53Measured with a ruler
Viewing distance (cm)d57Measured eye-to-screen
All three must describe the display the subject looks at. Nothing in the browser can check this, and getting it wrong scales every angle in the stimulus without leaving any other trace: the log will faithfully record the numbers it was given.

Which pixels?

A modern display often has more physical pixels than the browser counts. The number this field wants is the one the browser sees, and auto-detection fills it in correctly. The reason to know about it is that a figure read off the monitor's specification sheet may be a different number — and using that one silently makes every size in the stimulus wrong.

On a high-resolution laptop panel, for instance, the specification says 3584 pixels across while the browser works in 1792. Entering 3584 would halve every spatial frequency and double every mask: a grating asked for at 1 c/deg would be presented at 0.5, and a 2° mask would cover 4°. Nothing in the recording would show it.

The technical version: CSS pixels and the device pixel ratio

Wpx is in CSS pixels — the coordinate system the browser lays out and draws in. The canvas is sized from window.innerWidth, all drawing coordinates are canvas pixels, and pixelsPerDegree converts between those and visual angle, so every quantity in the chain shares that unit.

The panel's native resolution differs from it by the device pixel ratio, reported as window.devicePixelRatio and equal to 2 on a typical Retina or HiDPI display. Multiplying screen.width by that ratio yields the native resolution, which is the number on the specification sheet and the wrong unit here: it scales pixelsPerDegree by the ratio, and every angle with it. The ratio is recorded in the log under screen_info.device_pixel_ratio, so a suspect session can be checked afterwards.

Presenting on a second monitor

When the stimulus is presented in a separate window on another display — the usual arrangement, with the operator's settings on one screen and the subject's stimulus on another — the geometry has to describe the second monitor, not the first.

Auto-detection can only report the screen the settings window is on. The physical width in centimeters is something no browser can supply at all, on either screen. Both therefore need attention when the two displays differ, and they usually do: a laptop panel and an external monitor rarely share a pixel size.

The stimulus window reports which display it is on, and when that differs from the settings window the Screen section says so and gives the width the presentation display reports. Measure that monitor's physical width, enter both, and check the viewing distance is the one to that screen.

It keeps reporting: change the presentation monitor's resolution, or drag the window to another screen, and the warning follows within about a second. The refresh-rate estimate on the settings panel also comes from the stimulus window whenever one is open, labeled stimulus display — the panel's own reading would describe the operator's screen, and 60 Hz against 120 Hz is a common mismatch. The exact rate is measured again in the presenting window at the start of every session, and that is what the timing uses and the log records. The APA paragraph and the refresh-mismatch warning on the settings panel use the same figure: the stimulus window's rate whenever one is open, marked as an estimate until a session has measured it, and never the rate of the settings window's own display.

A quick check costs nothing. The APA paragraph and the log both state the visual field the stimulus covered. If a full-screen stimulus on a 53 cm monitor at 57 cm reports about 50°, the geometry is right. If it reports 25° or 100°, the pixel width is out by a factor of two in one direction or the other.

From these, the suite computes pixels per degree of visual angle (ppd), used for all spatial calculations:

ppd = (2 · d · tan(0.5°)) / (Wcm / Wpx)

The factor 2 · d · tan(0.5°) is the physical width (cm) of one degree of visual angle at distance d. Dividing by Wcm/Wpx (cm per pixel) converts that physical width into pixels.

Worked example: 53 cm at 57 cm with 1920 px wide 
cm/px      = 53 / 1920          = 0.02760 cm
2·57·tan(0.5°) = 2·57·0.008727  = 0.9949 cm/deg
ppd        = 0.9949 / 0.02760   = 36.05 px/deg

The well-known “57 cm rule” gives ~1 cm per degree, hence ppd ≈ pixels-per-cm.

Visual field width

The full visual field subtended by the screen is reported in the APA description in both width × height degrees and as the half-width from fixation:

VFwidth = 2 · arctan(Wcm / 2 / d) · 180/π

The screen height in cm is back-calculated from the pixel aspect ratio (Wcm · Hpx/Wpx); for non-square pixels this is an approximation but adequate for almost all modern displays.

Visual angle calculations

Throughout the suite, sizes are entered in degrees of visual angle and converted internally to pixels via the ppd value. Reporting in both units (degrees and pixels) is standard practice and is done automatically in the APA description.

Frame rate measurement

Nothing here assumes 60 Hz. Before every session the stimulus watches how quickly the browser hands it frames, for about a second, and uses that rate for all the timing that follows. This is what lets the same settings produce the same durations on a 60 Hz monitor and a 120 Hz one.

The technical version: how the rate is measured

The stimulus runs in a measurement state for 60 frames with frameRate(999), which removes p5.js's internal throttle so the renderer follows the browser's requestAnimationFrame callback directly rather than a library-imposed cadence. The interval between successive frames is recorded and the median taken.

The median rather than the mean: a single slow frame would drag an average upwards and lengthen every duration derived from it, while it leaves the middle of the distribution alone. The figures are below.

What this measures is how often the browser delivered a frame — not the refresh rate of the display. The two are usually the same and sometimes are not, and the difference matters enough to be worth understanding before it appears in your data.

Delivered rate against display refresh

No browser API reports a display's refresh rate. screen does not expose it and neither does the Window Management API. The only quantity available to a web page is the cadence of its own animation callbacks, and on a machine with displays of different refresh rates that cadence need not be the one the subject sees.

It is not settled by which monitor the window is on, either. A browser moved entirely onto a 60 Hz display has been observed still receiving frames at the 120 Hz of another connected panel. Whatever decides it sits below the browser, so the suite reports the discrepancy without claiming a cause for it.

This is why the Screen section has an optional Display refresh (Hz) field. Read the value from the operating system's display settings for the monitor the subject looks at and enter it. When it disagrees with the measured delivery rate by more than five per cent, the page says so, and the methods paragraph and the log record both figures.

What a mismatch costs you. Whichever of the two rates is slower is what the stimulus is really quantized to, and the two directions cost you different things.

Frames arriving faster than the panel refreshes — 120 Hz delivered on a 60 Hz display — means only some of them are ever shown. Durations land on multiples of 16.7 ms rather than 8.3 ms, and an event shorter than one refresh, such as a two-frame sync flash, may fall between refreshes and never appear at all.

Frames arriving slower — 60 Hz delivered on a 120 Hz display — loses nothing: every frame is shown, each held over two refreshes. The cost is only that the timing is coarser than the panel could have resolved.

Either way the log faithfully records the durations it intended. Setting every connected display to the same refresh rate is the dependable remedy; the photodiode trace is what settles the question for a given recording.
measuredFPS = 1000 / median(deltaTime1..60)

The result is displayed in the Timing section of every stimulus and is reported in the APA description and the JSON log. Frame-locked timings (e.g. flash duration in frames, sync dot on-time) are converted to milliseconds using this measured value.

Variable refresh rates defeat the measurement. In adaptive-sync mode (G-Sync / FreeSync), and with the browser not running at peak load, the measured rate may not be the rate the stimulus actually runs at. For VEP work, set the display to a fixed refresh rate.
Why median rather than mean?

A single 33 ms frame from a browser hiccup at the start of a 16.67 ms-target session would shift the mean from 60.0 Hz to ~58 Hz. The median ignores such outliers as long as they are fewer than half the samples. With 60 samples, up to 29 jank frames can occur without affecting the result.

Luminance calibration

A pixel sent as V = 255 does not emit twice the light of one sent as V = 128 — the relationship is the display's gamma characteristic, and it differs between panels and between brightness settings. Calibration is the act of measuring it. With it, the suite can linearize the stimuli, state contrast in luminance rather than in code values, and report cd/m² in the log and the methods paragraph.

Without it, nothing breaks: sRGB is assumed, the stimuli work in relative units, and no luminance figure is reported. That is a defensible way to run a pilot. It is not a defensible way to publish a contrast.

Calibration models

ModelWhat you measureWhat it is good for
sRGB Lmax and Lmin only The luminance range is real; the curve between them is assumed to follow the sRGB standard. Reasonable on a compliant panel.
Power law (γ) Lmax, Lmin and one exponent Fits most CRTs and many LCDs with one number.
Measured Photometer readings at ten gray levels; optionally the R, G and B channels as well The only model that reports cd/m². Required for anything published.
Measure the channels if color matters. A gray-only measurement says nothing about how the primaries compare with each other, and the suite then has to assume it. For achromatic stimuli that is irrelevant. For anything chromatic — and for isoluminance in particular — it is the difference between a measurement and an assumption. See Contrast and photometry.

Practical steps

  1. Open display_calibration.html.
  2. Choose the model. For Measured, press ▶ Start guided measurement: the page shows full-screen patches one at a time while you read the photometer and type each cd/m² value.
  3. The fitted curve and a verification patch at V = 128 appear as you go, so a bad reading shows up immediately rather than at the end.
  4. Press ↓ Download .json file. This file is the record of the display state; keep it with the recording.
  5. Press Open gate with this calibration. The gate opens with it already loaded and passes it to every stimulus you launch.
A calibration is good for thirty days. The gate and every stimulus page mark a calibration older than 30 days and ask for a new one. Recalibrate sooner if the monitor's brightness or contrast settings change, or if the panel is replaced.

How the calibration reaches a stimulus

Two ways, and they are meant to cover different situations.

  • In the link. The gate encodes the whole calibration into the cal parameter and, when it knows the file name, adds cal_name beside it. Every stimulus reads both. This is the normal route, and it is the only one that works reliably when pages are opened as file://.
  • Loaded on the page itself. Each stimulus has Load calibration .json file… under its calibration status line. What you load there overrides whatever the link carried, and is written back into the link the page shows — so it travels on to the stimulus window and to anyone you give the link to. Reload the page to go back to the link's calibration.

The status line names what is in force: the model, Lmax, the date, and whether it came from a named file or only from a link. 

✓ Measured · 312 cd/m² · Jul 20, 2026 · file: monitor_a.json
✓ sRGB · 250 cd/m² · Jul 20, 2026 · temporary (from link)
⚠ No calibration — sRGB assumed, relative units

Temporary does not mean unreliable — the calibration is complete either way. It means no file name is known for it, so there is nothing to trace it back to. The log records the same thing under cal_source: a file name where one is known, otherwise url or none.

Browser storage is a shortcut, not an archive. The gate remembers the last calibration you gave it so you need not load the file every session. That memory is ordinary browser storage: clearing browsing data removes it, a private window never sees it, another browser or machine has nothing, and Safari deletes script-writable storage after about a week without interaction. The .json file and the saved link are what survive. Failure is at least visible — when the memory is gone the gate says there is no calibration, rather than quietly using an old one.
Why file:// forces the calibration into the URL

Browser storage is partitioned by origin. When pages are served over http, all the files in one folder share an origin and can therefore share storage. When they are opened directly from disk, most browsers treat each file as its own origin, so what the calibration page saves is invisible to the gate and the stimuli.

A link has no such restriction, which is why the calibration travels in one. It also means the gate's own memory does work under file://: the restriction is between different files, not between visits to the same one.

Balancing the two phases of a radial pattern

A radial grating puts more screen area into its coarse outer rings than into the fine central ones. One consequence is easy to miss: when such a pattern reverses, the two phases do not average to quite the same brightness, so the whole field flickers slightly at the reversal rate on top of the pattern change itself. The evoked response cannot distinguish the two.

With a calibration loaded, the suite measures that imbalance and shifts the pattern to remove it. The shift is reported in the log as dc_correction_cdm2 and stated in the methods paragraph, so it is part of the record rather than an invisible adjustment. It is applied only where it makes sense: always for reversal, for onset only when the pattern alternates, and never for motion onset, where a drifting pattern has no second phase to be balanced against. Flash needs none, a uniform field having no phases at all.

Without a calibration there is no correction. The imbalance is a luminance quantity and cannot be computed from code values alone, so an uncalibrated radial reversal carries whatever flicker the geometry produces. For a checkerboard the question does not arise: its two phases cover equal area by construction.
Gamma linearization and DC correction — how they work

The radial grating is built as a lookup table over one spatial cycle. Interpolating the two phase colors linearly in code values would not give a sinusoid on screen, because the display's response is not linear: with γ around 2.2 the result is visibly distorted.

Instead both endpoints are converted to luminance, the sinusoid is generated in luminance, and each entry is converted back to a code value through the inverse calibration. What varies sinusoidally is then the light, not the number.

For the measured model the forward and inverse functions are a Fritsch–Carlson monotone cubic spline through the photometer readings. Monotonicity is what guarantees the inverse exists and stays inside [0, 255].

DC correction for radial patterns

CMF weighting gives more screen area to the coarse peripheral rings than to the fine central ones. The two phases of a reversal therefore do not have the same area-weighted mean luminance, even with a perfectly sinusoidal LUT — the pattern would carry a luminance flicker on top of the reversal.

With a calibration active, the area-weighted mean of one phase is compared with the midpoint of the two phase luminances and the difference is added to every LUT entry. The shift is reported in the log as dc_correction_cdm2, in the same cd/m² as the other luminance fields, and stated in the APA paragraph.

It applies where it makes sense and nowhere else: always for reversal, for onset only when the pattern alternates, and never for motion onset, where a drift has no phase partner to be balanced against. Flash needs none — a uniform field has no phases.

Contrast and photometry

Every stimulus has two colors: light and dark for the patterns, flash and blank for the flash. Their Michelson contrast in luminance is what the stimulus actually delivers, and it is what goes into the log and the methods paragraph. You can set the colors directly, or state the contrast you want and let the page work them out.

Asking for a contrast

Type a Michelson contrast in percent and a mean luminance, then press Apply to colors. The two color fields are filled in with a pair that delivers them: 

L_high = L_mean × (1 + C)        L_low = L_mean × (1 − C)

Contrast and mean luminance are independent: changing one does not disturb the other. The mean luminance field is in cd/m² when a calibration is loaded and in relative units of full scale when none is, and the label next to it says which.

The button is a proposal, not a mode. It writes into the ordinary color fields and then steps back. Nothing stores the contrast you asked for; you can edit either color afterwards and the reported contrast follows what the colors actually are. This is deliberate — a stored target and an edited color would sooner or later disagree, and the log would be wrong rather than merely surprising.

The line under the button always describes the current colors: the contrast they deliver, their luminances when those can be reported, and what the luminance figures rest on. Because the colors are quantized to eight bits, the delivered contrast is rarely exactly the one requested; the line shows what was achieved, and that is the number that is logged.

If the display cannot reach the request — a high contrast about a mean luminance close to the panel's maximum, say — nothing is applied and the line says which channel ran out of headroom. Silently clipping to something else would put an unintended stimulus on screen.

Colors keep their hue

Each color moves along its own line towards black, in linear light, so its chromaticity is preserved and only its luminance changes. A red stays red and a green stays green; asking for 0 % contrast therefore gives the isoluminant version of the pair rather than collapsing both to a single mixed color.

That case is a stimulus in its own right: an isoluminant red–green pattern isolates the chromatic response from the luminance one. Two things are worth knowing before relying on it.

  • Eight bits set a floor. A pair asked to be isoluminant typically lands within a few thousandths of Michelson zero, not at zero. The residual is reported.
  • Photometric is not individual. Isoluminance computed from a display calibration is not isoluminance for a particular observer. If that distinction matters for your question, it has to be established per observer, for example by heterochromatic flicker photometry.

Pattern onset: the blank field

Pattern onset shows the pattern against a blank field and takes it away again. If the blank does not sit at the pattern's mean luminance, each onset carries a step in overall luminance on top of the pattern appearing — and the response cannot tell the two apart.

The onset page therefore offers Blank at pattern mean beside the button, on by default. When it is ticked, the page starts the blank at the mean luminance of the pattern colors as it opens, and Apply to colors moves it there again whenever it sets new colors; either way the blank keeps its own chromaticity and changes only in brightness. A link that sets hexBlank is reproduced as written — it is a recorded condition. Untick the box if you want the blank set by hand.

How luminance is worked out

A color's luminance is the black level plus what each channel contributes above its own dark point, weighted and summed. Two details of that sentence matter in practice.

Why each channel is measured from its own dark point

A channel driven to 0 still emits a little, and so does the panel as a whole. If a channel's contribution were measured from the gray black level rather than from its own, a channel at 0 would appear to still be emitting, and the black floor would be counted three times over. The error is negligible for bright colors and large for dark saturated ones — precisely the region where isoluminant pairs are set.

Where the channel weights come from

With all three primaries measured, their own curves carry the ratios between them. One common scale is then applied so that the three contributions add up to the directly measured white; the residual away from white is genuine non-additivity of the panel, and is left as it is.

Without them, the three channels share the gray curve, and weighting them equally would amount to claiming that every primary emits the same light. No display does. Green typically emits around three times what red does and nine times what blue does, so an equal weighting would make an isoluminant red–green pair a no-op — the two would already appear equal to the model.

The suite therefore falls back to the relative primary luminances of the BT.709 / sRGB color space: 0.2126 for red, 0.7152 for green, 0.0722 for blue, applied to linear light. They sum to one, so an achromatic color still reproduces the measured gray curve exactly. On a typical panel they land within about a percent of what a per-channel measurement gives; on a wide-gamut display they will not, since its primaries are not the BT.709 ones.

This is an assumption and the software says so. The log records luminance_basis as measured_channels or measured_grey_srgb_primaries, the line under Apply to colors ends with R/G/B measured or R/G/B assumed from sRGB primaries, and the APA paragraph cites the standards it took the numbers from.

Luminances are estimates, not session photometry. Every cd/m² figure the suite reports is computed from the calibration's transfer function, not measured while the subject was in front of the screen. The APA paragraph states this outright, so a methods section cannot accidentally claim more than was done.

Checkerboard pattern

Two of the stimuli (Pattern Reversal, Pattern Onset) provide a checkerboard option. It is rendered so that the four corners of the four quadrant sectors meet at the exact center of the display, which is the centered arrangement the ISCEV standard describes. Everything else about the pattern — check size, field size, contrast — is yours to set, and whether the result conforms is a question about your protocol. Check size is entered in degrees of visual angle and converted to pixels using the measured ppd.

Pixel-level parity calculation

Each pixel at (x, y) receives a check identity parity = ⌊(x − cx)/checkPx⌋ XOR ⌊(y − cy)/checkPx⌋, where checkPx = checkSize_deg · ppd. Even parity is rendered in the dark color, odd parity in the light color.

Reversal mechanism

Reversal is implemented as a 180° phase shift of a global lookup table (LUT) offset, swapping the two colors simultaneously across the entire pattern. The structure of the checkerboard never changes; only the assignment of color to each cell is inverted. This avoids any spatial motion artifacts during reversal.

Radial sinusoidal grating

The radial pattern is a fullscreen sinusoidal grating whose spatial frequency varies with eccentricity. The grating is concentric — the brightness of any pixel depends only on its radial distance from the center.

Phase and brightness calculation

For each pixel the suite computes the cumulative phase Φ(r) = ∫₀ʳ f(r') dr' in cycles, where f(r) is the spatial frequency at radius r. The fractional part of Φ(r) is the LUT index used to look up the rendered brightness. The brightness ramp is sinusoidal:

p = ½ + ½ · sin(2π · Φ(r))

The result interpolates between the dark and light phase colors at full amplitude: p reaches 0 and 1, so the grating spans the whole pair. The pattern's contrast is therefore the contrast of the two colors and nothing else — there is no separate depth-of-modulation setting to multiply it by. See Contrast and photometry.

With a calibration active the interpolation happens in luminance rather than in code values, so what varies sinusoidally is the light on screen — see Gamma linearization.

CMF weighting

For both the Pattern Reversal / Onset radial mode and the Motion Onset stimulus, spatial frequency varies with eccentricity following a cortical magnification factor (CMF) profile (Kremláček et al., 2004):

CMF profile and frequency interpolation formula
CMF(e) = 1 / (0.1 · e + 1)

where e is eccentricity in degrees. Spatial frequency is interpolated between cent_freq and per_freq using this profile:

f(r) = cent_freq + (per_freq − cent_freq) · (1 − CMF(r)) / (1 − CMF(R))

This guarantees f(0) = cent_freq and f(R) = per_freq, where R is the maximum canvas radius.

Why this profile?

The visual cortex has roughly logarithmic representation of eccentricity: more neurons per degree at fixation than in the periphery. By scaling spatial frequency inversely, the radial grating produces approximately equal responses per unit cortical surface area, which improves signal-to-noise ratio in single-trial VEPs and reduces over-representation of the central few degrees.

Reference: Kremláček, J., Kuba, M., Kubová, Z., Chlubnová, J., & Szanyi, J. (2004). Motion-onset VEPs to translating, radial, rotating and spiral stimuli. Documenta Ophthalmologica, 109, 169–175.

LUT phase mechanism

Both pattern types share the same rendering pipeline: a pre-computed per-pixel index buffer is used on every frame with a single global offset that shifts the entire pattern phase. This allows instantaneous pattern reversal and smooth motion with minimal CPU cost.

LUT implementation details

A per-pixel index buffer baseIdx stores each pixel's lookup-table address. The rendered color is LUT[(baseIdx[p] + globalOffset) & LUT_MASK]. With LUT_SIZE = 1024, a global offset of LUT_SIZE/2 shifts every pixel's lookup by 180° — equivalent to a phase-inversion of the entire pattern in a single integer add per pixel.

This is exploited by:

  • Pattern reversal — toggling the offset between 0 and LUT_SIZE/2 at each reversal event.
  • Pattern onset (alternation option) — flipping the offset on every even-numbered trial to avoid long-term luminance adaptation.
  • Motion onset — incrementing the offset continuously to produce smooth radial motion.

Because baseIdx is computed once per session, rendering each frame is just a tight pixel loop — fast enough for native display refresh on integrated graphics.

Masking

Masks replace pixels with a uniform mask color (default #808080). They are applied after the pattern is drawn and before the fixation and sync dot, so the fixation cross is always visible regardless of the mask configuration.

Mask types

Quadrant naming

Quadrants are numbered following the standard mathematical convention: Q1 = top-right, Q2 = top-left, Q3 = bottom-left, Q4 = bottom-right.

How masks are computed

On session start, the suite pre-computes a list of pixel indices for every active mask. During each frame's blit step, the mask color is written into those indices in a tight loop — there is no per-frame distance calculation. This keeps the per-frame cost constant regardless of mask geometry.

Synchronization

Each stimulus draws a small square (the “sync dot”) at a configurable screen position. It lights up in its trigger color for a few frames at each sync event and is black at all other times — on every stimulus, flash included. A photodiode taped to the screen at this position produces a clean step that can be used as a trigger for EEG / MEG recordings.

Dot color

The trigger color is white by default, which suits a photodiode that measures luminance. With an RGB photodiode, choose a single primary — #ff0000, #00ff00 or #0000ff — so that only one channel responds. The color is set with the swatch beside the Synchronization heading on each stimulus page, or in the gate.

The gate holds three colors, one per stimulus. Stimulus 1 is the color every single-stimulus page uses (flash, reversal, onset, motion). Stimuli 2 and 3 apply only to pages that present more than one stimulus in a session (Oddball VEP), where each stimulus fires the dot in its own color so the recording can tell them apart. The gate warns when two stimuli share a color.

A single primary is much darker than white. Pure blue carries roughly 7 % and pure red roughly 21 % of the luminance of white. A luminance photodiode whose threshold was set for a white dot may not respond to them. Check the trigger after changing the color.

A radial sinusoidal grating that alternates between a stationary HOLD phase and a moving phase. Motion is produced by smoothly advancing the global LUT phase offset, giving the impression of expansion or contraction (randomized per trial).

The temporal frequency parameter temporal_freq controls the rate of LUT-phase advance. Because the spatial frequency varies with eccentricity (CMF weighting), the apparent angular speed at radius r is:

Oddball VEP (oddball_vep.html)

A frequent standard and a rare deviant — and, if wanted, a third stimulus — appear one at a time at the center of the screen, in a pseudorandom order. Each trial is built like a pattern-onset trial: the stimulus is shown for the On duration, then the background alone for the Off duration. The sync dot lights in a different color for each stimulus, so the recording knows which one was shown without any other connection to the stimulus computer.

Stimuli

Each stimulus is a shape: a built-in X, O or +, or a shape from an SVG file. All are drawn Shape height degrees tall — the height of what is drawn, not of an invisible frame around it — and an SVG keeps its own width-to-height ratio. Stroke width sets the line thickness of the built-in shapes. Every shape has its own color; all share one Background, which also fills the screen between stimuli.

Shapes are drawn with exactly two luminance levels, their color and the background, with no smoothed edges: a smoothed edge would contain colors whose luminance the calibration does not describe. Small shapes therefore have visibly stepped edges.

Contrast with Apply to stimulus colors sets every stimulus color to that Michelson contrast against the background. The background stays where it is, since all stimuli share it; each color keeps its hue and stays brighter (or darker) than the background. X and O are not equal in light. Shapes of the same height draw different areas, so they emit different amounts of light, and part of a difference in the response can come from that alone. The page shows each shape's size and drawn area and says when the areas differ; the log and the methods text record them.

Using an SVG file

Choose SVG file… as the shape and load the file. The shape is whatever the SVG paints opaquely; its own colors are ignored, and the color comes from the page, where the calibration applies. Use one file per stimulus. The file is checked and cleaned when it is loaded:

  • Refused: text (it would be drawn with whatever fonts the computer has — convert text to paths, “Object to Path” or “Create Outlines” in the editor), embedded or linked images, links to anything outside the file, scripts.
  • Removed: editor metadata, comments, titles.
  • Size: at most 16 kB after cleaning. A plain shape is usually well under 1 kB; editors add a great deal around it.
  • Background: the file must have a transparent background. A shape that fills its whole box is flagged — usually a forgotten background rectangle.

The cleaned SVG travels inside the link, like the calibration, so it does not have to be loaded again: a condition added to the gate keeps it, and so does the protocol file. The log contains the file itself and its SHA-256 fingerprint.

The technical version: how the order is generated

The non-standard trials split the standards into gaps. The required minimum is placed in each gap first; the remaining standards are spread over the gaps as a uniformly random composition, and the non-standard stimuli are put in a uniformly random order (Fisher–Yates). The random numbers come from the mulberry32 generator, seeded with seed: the same seed gives the same order in every browser. With a longest run set, arrangements that break it are drawn again. The off-phase jitter comes from a separate stream of the same seed, so changing the jitter never changes the order.

Log file format

With Save log ticked, a JSON file is written when the session ends, whether it ran to completion or was stopped. The download is offered by whichever window ran the stimulus, and the file names itself after the session it records:

Software timestamps are not photon timestamps. All *_ms and *_perf_ms fields come from performance.now() at the moment the event handler runs. Browsers deliberately coarsen that clock — to 0.1 ms in Chrome, and to as much as 1 ms in some other browsers — and the moment recorded is when the frame was requested, not when it reached the screen. For the time light left the display, use the photodiode signal in your recording.

Log analyzer

vep_log_analyzer.html reads any of these files and reports descriptive statistics — median, IQR, MAD (×1.4826), mean ± SD, n, min, max — with the deviation from the configured target, and an APA paragraph that can be copied out. Everything happens in the browser; nothing is uploaded.

Beside the timing it restates the session itself: the stimulus and the suite and engine versions, the renderer and its parity result, the number of pauses, the calibration with its type, date and source, the Michelson contrast, the luminance basis and the estimated luminances. Fields a log does not carry are shown as (not recorded) rather than left blank.

Stimulus-specific metrics it derives from the log:

  • Flash: inter-flash interval (vs. 1000/flashFreq), flash duration
  • Reversal: inter-reversal interval (vs. half-period)
  • Onset: real ON duration, real OFF duration, trial period
  • Motion: real MOVE duration, real HOLD duration, frames per MOVE, plus direction balance (expanding vs. contracting)

APA description

Below each stimulus form, under APA-style report, the page shows a methods paragraph written from the settings actually in force; a click copies it to the clipboard. It is written from the same values as the log, so the two cannot disagree. The structure is the same across all stimuli:

  1. Stimulus type and pattern properties, with the colors used
  2. Temporal parameters and total stimulation time
  3. The interval before the first stimulus and after the last
  4. Display geometry: pixels, centimeters, viewing distance, visual field in degrees, pixels per degree, and the frame rate with how it was obtained
  5. Synchronization patch, fixation cross and active masks, where used
  6. The display calibration, the contrast delivered (in percent), and — with a measured calibration — the estimated luminances
  7. Which renderer drew the frames
  8. Operator pauses, if any

The paragraph cites no literature. It describes the settings that were used and nothing beyond them. A reference to the ISCEV standard or to the motion-onset recommendations would hold only if the parameters follow them, and the page cannot know whether they do — whether a configuration conforms depends on the protocol rather than on the software. Add the references yourself where they apply: they are listed in Citation & license, together with what the ISCEV standard does and does not settle here.

What it says about luminance, and why

The wording around photometry is deliberate, because this is where a methods section can most easily claim more than was done.

  • With no calibration it states that none was in force, that sRGB was assumed, that luminances are relative, and gives the contrast under that assumption. Nothing is quietly omitted.
  • With a calibration it names the model and Lmax and gives the Michelson contrast in luminance.
  • With a measured calibration it adds the phase luminances and their mean, and says in the same sentence that these are estimates derived from the display calibration and not photometric measurements of the session.
  • Where the primaries were not measured individually it says so and cites the BT.709 / sRGB coefficients it used instead, so a reader can judge how far a chromatic or isoluminant claim rests on assumption.
The contrast reported is the contrast delivered. It is computed from the colors as they stand, after 8-bit quantization — not from a target you asked for. If you set 50 % and the display could only reach 49.9 %, the paragraph says 49.9 %.

Why the calibration travels in the link rather than in storage

cal holds the entire calibration object, base64-encoded. A full measured RGB calibration comes to roughly 1 600 characters and a complete stimulus link to about 2 300, which every current browser accepts without difficulty.

Carrying it this way is what makes a link self-contained and what makes the suite work from file://, where browser storage is not shared between files. cal_name travels beside it so the log can name the file the calibration came from instead of merely recording that something arrived in a link.

Troubleshooting

Starting a session

Start is grayed out and will not respond

With Fullscreen ticked, Start stays locked until the presenting window reports that it really is full-screen. Click once inside the stimulus window, or press F there. If you opened a separate window, it is that window which has to be full-screen, not the settings window.

The check accepts an OS-maximized window and a macOS virtual desktop as well as the browser's own full-screen mode — what it will not accept is a window with anything visible around it. If you deliberately want to present in a window, untick Fullscreen and Start unlocks.

The stimulus window is stuck on “starting…”

The settings window has asked the stimulus window to begin and is waiting for it to confirm. Check the stimulus window is still open and was not reloaded independently; closing it and pressing ↗ New window again re-establishes the connection.

Ticking Fullscreen does nothing to the open stimulus window

It does reach that window, but a browser only grants full-screen to a window in response to something done in that window. The prompt appears there; one click or F completes it. There is no need to close and reopen the window.

The stimulus window opens blank, or does not open at all

Popups have to be permitted for the page. Allow them for this file or site and press ↗ New window again.

Calibration

The gate says there is no calibration, though one was saved

What the gate remembers is browser storage, and it is discarded by clearing browsing data, by using a private window, by switching browser, profile or machine, and in Safari after about a week without interaction. Load the .json again, or open the link you saved with the calibration in it. This is why the file and the link are the durable forms and the memory is only a shortcut.

The calibration page saved, but the stimuli do not see it

Opened as file://, each file is its own storage origin, so nothing saved by one page is visible to another. Use Open gate with this calibration, or download the .json and load it in the gate or on the stimulus page. The calibration then travels in the link, which has no such restriction.

The gate reports that vep_engine.js could not be loaded

The engine file has to sit in the same folder as the gate and the stimuli. Without it the gate cannot encode a calibration into a link, so it stops rather than build links that silently lack one.

Mean luminance is in the wrong units, or a value looks absurd

The field is in cd/m² with a calibration loaded and in relative units of full scale without one; the label beside it says which. Loading a calibration converts your value so it keeps the same fraction of the display's range — it is not overwritten with a default. Clearing the field and leaving it empty makes the page suggest half of Lmax.

Colors and contrast

Apply to colors refuses with “outside the display range”

The requested pair cannot be shown: a high contrast about a mean luminance close to Lmax needs a bright phase brighter than the panel can emit, and a mean close to black needs a dark phase below its black level. The message names the channel that ran out of headroom. Lower the contrast, move the mean luminance towards the middle of the range, or choose a less saturated color — a saturated primary has much less headroom than white.

Asking for 0 % contrast on a red / green pair changes almost nothing

Check the line under the button. If it ends with R/G/B assumed from sRGB primaries, the display's primaries were never measured and their relative luminances are being assumed. The result is a reasonable approximation on a standard panel and can be some way off on a wide-gamut one. Measure the R, G and B channels in the calibration page for chromatic work.

The contrast in the log is not the number I typed

It is not meant to be. What is logged is the contrast the colors actually deliver after rounding to 8-bit values, which is usually a fraction of a percent from the request. Nothing stores the requested figure — the colors are the stimulus, and the log describes the stimulus.

A copied link opens with different colors

It should not: every stimulus writes its colors into the link and reads them back. If it happens, check that the whole link was copied — the calibration parameter alone runs to well over a thousand characters, and a link truncated by an email client or a chat window will lose whatever came after the cut.

Display and timing

The frame rate measurement reads ~120 Hz on a 60 Hz monitor

Some browsers drive requestAnimationFrame at 120 Hz on modern systems. Check the actual refresh rate in the operating system's display settings and that the browser's compositor matches it. The measured value is what the timing calculations use, so a wrong reading propagates into every frame-locked duration.

The pattern looks pixelated or aliased near fixation

For the radial grating, high central frequencies (cent_freq above about 4 c/deg at low pixels-per-degree) produce moiré near the center. Reduce cent_freq, increase the central mask radius, or increase the viewing distance. The checkerboard is not affected.

The log says canvas2d though WebGL is available

The stimulus checks that the GPU shader reproduces the CPU reference for the exact configuration in use, and falls back to Canvas 2D when it does not. That is the intended behavior: the same stimulus is presented either way, only more slowly. The parity test page shows which configuration failed and by how much. &webgl=0 forces the CPU path deliberately.

Sync dot does not trigger the photodiode

Check three things in order. That the photodiode sits over the dot's pixel coordinates — 32, 32 by default, in the top-left corner. That the on-time in frames is long enough for the amplifier's rise time; try 4 frames if 2 is too brief. And that the sync event flag for this stimulus is enabled, for instance syncOnReversal for pattern reversal. If the dot color was changed from white, check also that the photodiode responds to it: a single primary is much darker than white.

Files and output

The log download is blocked

Running from file://, some browsers show a warning bar before allowing a download. Accept it. Served from a web server, the prompt does not appear.

Copying the URL or the APA paragraph fails

Clipboard access needs a recent user gesture and a secure context. The text is always shown on the page as well, so it can be selected and copied by hand.

Which log belongs to which run?

The file name carries the stimulus, the session's start time and the session note, so runs in one folder identify themselves without being opened. If the note was left empty the timestamp still separates them, and session_start_iso inside the file gives the same moment to the millisecond.

What is and is not verified

Some properties of this suite have been checked systematically and some rest on judgment. The distinction is worth stating, because it tells you where to look first when something behaves unexpectedly.

  • Checked by simulation: the timing state machines, the frame counting model of each stimulus, the full-screen decision table, the contrast solver across color pairs and edge cases, the luminance model against measured and assumed channel data, and the round trip of the calibration through a URL.
  • Checked statically: that every message sent has a handler, that no element identifier is duplicated, that the markup is balanced, and that what each page writes into a link it also reads back.
  • Established by measurement, by you: everything photometric. The suite computes from the numbers you supply; it does not measure the display.
  • Established by looking at the screen: rendering, appearance, real timing on real hardware, and browser behavior. No amount of static checking substitutes for running the stimulus on the machine that will record it.
Durations rest on the measured refresh rate. Frame-locked durations are computed from the rate measured at the start of the session. Software timestamps come from performance.now() at the moment the event handler runs, which is the closest the browser can report — but it is when the instruction was issued, not when the photons left the display. For timing that has to withstand scrutiny, the photodiode trace is the measurement and the log is the annotation.

How this software was written

The suite was developed by the author working with Claude, an AI assistant made by Anthropic. The division of work is worth stating plainly, because it bears on what the code has and has not been checked against.

The assistant wrote and revised the code to those decisions, and verified it by static checks and by simulating the timing, state machines and photometric calculations outside the browser.
